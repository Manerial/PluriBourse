# Decision Log — PluriBourse Product Brief

## Session: 2026-06-08

### D-01 — Barcode format: Code 128
**Decision:** Use Code 128 barcode format.
**Reason:** EAN-13 is limited to 12 data digits; the desired scheme (YYYYMMDD + 6-digit vendor + 3-digit article = 17 digits) exceeds that limit. Code 128 supports variable-length alphanumeric sequences and is universally supported by standard USB barcode scanners (douchettes). Labels printed on standard adhesive paper sheets via a regular printer.

### D-02 — No integrated payment processing
**Decision:** Out of scope for v1.
**Reason:** The association handles payments externally (cash/CB). The app records sales but does not process transactions.

### D-03 — Seller portal: out of scope
**Decision:** Sellers have no access to the application.
**Reason:** Workflow is managed entirely by bénévoles on behalf of sellers. Sellers interact only via paper documents (deposit slip, payout document).

### D-04 — Commission rate: configurable by admin
**Decision:** Commission rate (default 20%) is configurable in admin settings.
**Reason:** May change between editions; should not require code changes.

### D-05 — Event phase lifecycle: admin-controlled
**Decision:** Four sequential phases — Deposit, Sale, Post-sale, Closed — triggered manually by the admin.
**Reason:** Once sales start, no new deposits are accepted. Once post-sale starts, no new sales. Prevents data integrity issues. It is still possible to roll back.

### D-06 — Printing: centralized print endpoint
**Decision:** All print jobs (labels, deposit slips, invoices, reports) go through a centralized server-side print endpoint rather than workstation-local printing.
**Reason:** Most workstations are Linux-based; avoiding per-workstation printer drivers reduces setup complexity. One shared printer connected to the server handles all output.

### D-07 — Bénévole accounts: individual logins
**Decision:** Bénévoles have individual user accounts (simple username/password).
**Reason:** Traceability requirement — in case of errors on event day, the admin needs to identify which bénévole performed which action.

### D-08 — Multi-edition history: persistent
**Decision:** Seller profiles persist across editions. Per-edition data (inventory, sales) is scoped to each edition.
**Reason:** Allows returning sellers to be found by name/email without re-entering their details each year.

### D-09 — Technical stack
**Decision:** Spring Boot backend + Angular frontend, web app with central server.
**Reason:** Developer familiarity. Linux-compatible by default (browser-based).

### D-10 — Edition naming: free-form
**Decision:** Edition names are free-form strings (no enforced format).
**Reason:** The app targets multiple associations running different event types (toys, books, skis, etc.) potentially multiple times per year. A fixed format (year only) would be too restrictive.

### D-11 — Barcode scanner keyboard layout compatibility
**Decision:** The Angular POS scan input component handles OS keyboard layout mismatches transparently using `event.code` (physical key position) instead of `event.key` (layout-dependent character). No configuration required on workstations.
**Reason:** USB HID barcode scanners emulate a keyboard. On AZERTY systems, raw key codes for digits 2–6 are mapped to é,",',(,- instead of 2,3,4,5,6. This is a known event-day failure mode. Intercepting at the frontend (before browser character translation) is the only reliable fix — the server receives already-corrupted input if not handled here.

### D-12 — Minimum server spec: Raspberry Pi 4 (2 GB RAM)
**Decision:** Minimum supported server hardware is a Raspberry Pi 4 with 2 GB RAM (or any equivalent 64-bit machine). SSD/USB storage is strongly recommended; microSD is explicitly flagged as unreliable for production database writes.
**Reason:** JVM (Spring Boot) + MariaDB + OS fits comfortably within 2 GB with proper JVM heap tuning. The load profile is light (100 sellers, 1700 items, 3 concurrent users, short event-day bursts). Storage I/O on microSD is the main risk factor, not RAM.

### D-13 — Deployment model: self-hosted, one instance per association
**Decision:** Self-hosted. Each association runs its own independent instance.
**Reason:** Simpler to develop (no multi-tenancy), associations own their data, no ongoing hosting cost or dependency. A detailed installation guide for non-technical users compensates for the lack of a managed service.

### D-14 — Installation guide: in scope for v1
**Decision:** A detailed installation guide targeting non-technical users is a v1 deliverable.
**Reason:** Without it, self-hosted distribution is limited to technically savvy users. The guide is what makes the "offer to other associations" vision viable.

### D-15 — Seller collection tracking
**Decision:** Each seller gets a "collected" flag once they have retrieved their payout and unsold items. Reports surface uncollected sellers.
**Reason:** The association needs to follow up on sellers who don't return to collect.
