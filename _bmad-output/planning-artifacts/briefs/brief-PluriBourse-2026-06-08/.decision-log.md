# Journal des Décisions — Brief Produit PluriBourse

## Session : 2026-06-08

### D-01 — Format de code-barres : Code 128
**Décision :** Utiliser le format de code-barres Code 128. Numéro sur 8 chiffres : 4 chiffres pour le numéro du vendeur dans l'édition + 4 chiffres pour le numéro de l'article dans l'inventaire du vendeur. Le numéro lisible sous le graphique est affiché au format XXXX-XXXX.
**Raison :** Code 128 supporte des séquences numériques de longueur variable et est universellement pris en charge par les scanners USB standard (douchettes). Le schéma 4+4 permet jusqu'à 9 999 vendeurs et 9 999 articles par vendeur par édition — largement suffisant pour une bourse. La séparation visuelle XXXX-XXXX facilite la saisie manuelle en cas de code illisible.

### D-02 — Pas de traitement de paiement intégré
**Décision :** Hors périmètre pour la v1.
**Raison :** L'association gère les paiements en externe (espèces/CB). L'application enregistre les ventes mais ne traite pas les transactions.

### D-03 — Portail vendeur : hors périmètre
**Décision :** Les vendeurs n'ont pas accès à l'application.
**Raison :** Le flux est entièrement géré par les bénévoles au nom des vendeurs. Les vendeurs interagissent uniquement via des documents papier (bordereau de dépôt, document de reversement).

### D-04 — Taux de commission : configurable par l'admin
**Décision :** Le taux de commission (défaut 20 %) est configurable dans les paramètres admin.
**Raison :** Peut changer entre les éditions ; ne devrait pas nécessiter de modifications du code.

### D-05 — Cycle de vie des phases : contrôlé par l'admin
**Décision :** Quatre phases séquentielles — Dépôt, Vente, Post-vente, Clôturé — déclenchées manuellement par l'admin.
**Raison :** Une fois la vente commencée, plus aucun dépôt n'est accepté. Une fois la post-vente commencée, plus aucune vente. Prévient les problèmes d'intégrité des données. Un retour en arrière reste possible.

### D-06 — Impression : point d'impression centralisé
**Décision :** Tous les travaux d'impression (étiquettes, bordereaux de dépôt, factures, rapports) transitent par un point d'impression centralisé côté serveur plutôt que par une impression locale sur les postes.
**Raison :** La plupart des postes fonctionnent sous Linux ; éviter les pilotes d'imprimante par poste réduit la complexité de configuration. Une seule imprimante partagée connectée au serveur gère toutes les sorties.

### D-07 — Comptes bénévoles : connexions individuelles
**Décision :** Les bénévoles ont des comptes utilisateurs individuels (nom d'utilisateur/mot de passe simple).
**Raison :** Exigence de traçabilité — en cas d'erreur le jour de l'événement, l'admin doit pouvoir identifier quel bénévole a effectué quelle action.

### D-08 — Historique multi-éditions
**⚠ Révisé :** Les profils vendeurs sont propres à chaque édition (voir brief §Périmètre et PRD FR-019). Les données par édition (inventaire, ventes) sont cloisonnées par édition.

### D-09 — Stack technique
**Décision :** Backend Spring Boot + frontend Angular, application web avec serveur central.
**Raison :** Familiarité du développeur. Compatible Linux par défaut (basé navigateur).

### D-10 — Nommage des éditions : libre
**Décision :** Les noms d'éditions sont des chaînes libres (aucun format imposé).
**Raison :** L'application cible plusieurs associations organisant différents types d'événements (jouets, livres, skis, etc.) potentiellement plusieurs fois par an. Un format fixe (année uniquement) serait trop restrictif.

### D-11 — Compatibilité disposition clavier du scanner
**Décision :** Le composant Angular de saisie scanner POS gère les incohérences de disposition clavier OS de façon transparente en utilisant `event.code` (position physique de la touche) au lieu de `event.key` (caractère dépendant de la disposition). Aucune configuration requise sur les postes.
**Raison :** Les scanners USB HID émulent un clavier. Sur les systèmes AZERTY, les codes de touche bruts pour les chiffres 2–6 sont mappés sur é,",',(,- au lieu de 2,3,4,5,6. C'est un mode d'échec connu le jour de l'événement. L'interception côté frontend (avant la traduction de caractère par le navigateur) est le seul correctif fiable — le serveur reçoit une entrée déjà corrompue si elle n'est pas gérée ici.

### D-12 — Spec serveur minimale : Raspberry Pi 4 (2 Go RAM)
**Décision :** Le matériel serveur minimum supporté est un Raspberry Pi 4 avec 2 Go RAM (ou toute machine 64 bits équivalente). Le stockage SSD/USB est fortement recommandé ; la carte microSD est explicitement signalée comme peu fiable pour les écritures en base de données en production.
**Raison :** JVM (Spring Boot) + MariaDB + OS tient confortablement dans 2 Go avec un réglage approprié du tas JVM. Le profil de charge est léger (100 vendeurs, 1 700 articles, 3 utilisateurs simultanés, courts pics le jour de l'événement). L'I/O de stockage sur la carte microSD est le principal facteur de risque, pas la RAM.

### D-13 — Modèle de déploiement : auto-hébergé, une instance par association
**Décision :** Auto-hébergé. Chaque association gère sa propre instance indépendante.
**Raison :** Plus simple à développer (pas de multi-tenant), les associations possèdent leurs données, pas de coût d'hébergement continu ni de dépendance. Un guide d'installation détaillé pour utilisateurs non techniques compense l'absence de service géré.

### D-14 — Guide d'installation : dans le périmètre de la v1
**Décision :** Un guide d'installation détaillé ciblant les utilisateurs non techniques est un livrable v1.
**Raison :** Sans lui, la distribution auto-hébergée est limitée aux utilisateurs techniquement compétents. Le guide est ce qui rend viable la vision « offrir à d'autres associations ».

### D-15 — Suivi de la collecte vendeur
**Décision :** Chaque vendeur reçoit un drapeau « collecté » une fois qu'il a récupéré son reversement et ses invendus. Les rapports signalent les vendeurs non collectés.
**Raison :** L'association a besoin de relancer les vendeurs qui ne reviennent pas récupérer.
